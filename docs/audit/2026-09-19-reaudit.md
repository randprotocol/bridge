## 1. Findings

### H-1 — Tron USDT could be locked but never released · FIXED

`SafeTransfer` rejected a 32-byte `false` return. Tron mainnet USDT
(`TR7NHqjeKQxGTCi8q8ZY4pL8otSzgjLj6t`) moves the funds in `transfer` and then returns `false`; its
`transferFrom` returns `true`. Checked keylessly against `api.trongrid.io` with
`triggerconstantcontract`: USDT `transfer` → `0x00…00`, USDT `transferFrom` → `0x…01`, USDC
`transfer` → `0x…01`. So a lock succeeded (the pull uses `transferFrom` and the delta matched),
the note minted on Rand, and every `release` reverted `TransferFailed` — on a contract with no
upgrade and no rescue path, for the token the launch policy names first
(`docs/architecture.md` §10.1). The existing test covered only the no-return shape.

Fix: `release` pays through `_push`, the mirror of `_pull`: the return data is ignored and the
bridge's own balance must fall by exactly the amount paid, else `TransferAmountMismatch` and the
digest stays unspent. A token that returns `false` and moves nothing is caught by the delta
instead of the return value. Tests: `test_release_tron_usdt_style_transfer_returns_false`,
`test_release_rejects_transfer_that_moves_nothing`.

### M-1 — An attestation does not name its network · DOCUMENTED + TOOLING GUARD

`mu` covers the body only; testnets share the mainnet bridge chain ids and the governance emitter
is one constant. If a guardian key set serves both a testnet and mainnet bridge, a testnet
rotation 0→1 verifies on every mainnet endpoint and the mainnet ledger while mainnet is at index
0; with a shared `RAND_EMITTER`, testnet burns release mainnet custody. The same holds for an
endpoint redeployed under the same set and emitter (empty consumed set). The shared test vectors
use publicly known guardian secrets.

Now: `spec/ATTESTATION.md` §3.5 and `deploy/README.md` make distinct guardian keys and a distinct
emitter per network a MUST; `check_network_separation` in `deploy/lib.sh` refuses a mainnet
deployment whose `GUARDIANS` or `RAND_EMITTER` appear in any non-mainnet deployment record.
A per-deployment governance emitter would separate the domains in the wire format; that is a
change to every verifier and the vectors and is left to the external-audit round.

### Open (tracked, not fixed here)

| id | sev | finding |
|---|---|---|
| O-1 | low | **Solana: `n >= 9` needs a v0 transaction.** A seven-signature release is 1,224 of 1,232 bytes; the 40-byte compute-budget instruction the recoveries need (7 × 25k, plus nine `find_program_address` calls) does not fit. `Config.bump` is stored and never used; storing and using bumps would cut the compute. The launch set (`n = 6`) fits. Native `solana-program-test` does not meter compute, so no test covers it. |
| O-2 | low | **No on-chain bound on a rotated set's size.** A rotation to `n = 25` signed by five of six is accepted on Solana, after which neither a release (17 signatures) nor the next rotation fits a transaction: custody is frozen until a program upgrade. A `MAX_GUARDIANS` is a parity rule — every verifier or none. |
| O-3 | low | **Solana has no `SetPauser`.** The EVM side has `setPauser`; on Solana a compromised pauser can re-pause after every admin `Unpause` until a program upgrade. |
| O-4 | low | **`Lock` can be griefed on Solana.** Every lock names `["msg", config.sequence]`; dust locks (≈0.0023 SOL rent each) make concurrent honest locks fail `InvalidPda`. Key the message account by `(owner, nonce)` and assign the sequence inside the instruction. |
| O-5 | low | **Sub-unit dust is lost.** For a token with fewer than 8 decimals the release floors: a burn of 199 attested units of a 6-decimal token pays 1 native unit and strands 99 in custody; a burn below 100 can never be released (`ZeroAmount`). Custody stays solvent. `check_burn` on Rand does not know the decimals; the wallet must enforce the granularity, or `AssetInfo` must carry it. |
| O-6 | info | The Solana verifier hashes `att.body.encode()`, a re-encoding, where architecture §11 says the wire bytes. Equal today because the codec is canonical; `Attestation::body_bytes` exists for this. |
| O-7 | info | A release recipient that is itself a token account lands at the ATA derived from that address, which nobody can sign for. `cli/keys.rs` applies mode 0600 only when it creates the file. The CLI's guardian parser drops empty entries. |
| O-8 | info | Relayer fee goes to `msg.sender`, so submission is front-runnable for the fee (by design). A blacklisted USDT/USDC recipient makes that one burn unreleasable. A rotated-away set signs releases for 24 h; pausing is the only mitigation — runbook. |
| O-9 | info | Vector gaps — no shared negative vector for: recovery id ≥ 2 (no EVM unit test either), zero amount, amount in (u64, u128], rotation with a skipped/reapplied index, duplicate or zero key, `n = 0`, wrong emitter for the payload type, non-zero upper 12 bytes, zero recipient, the `now == expires_at` and `s == half_n` boundaries. Most have per-verifier unit tests. |
| O-10 | info | `Deploy.s.sol`'s `CHAIN=tron` branch skips the chain-id check. Genesis `check_bridge` admits up to 367 guardians, more than a one-byte rotation can ever reproduce. |

## 2. Invariants re-verified (all three verifiers, against `spec/ATTESTATION.md`)

Envelope `6 + 66n`, body header 51, transfer payload exactly 133, upgrade payload exactly `6 + 20n`
(never 133), unknown payload id refused: no trailing bytes anywhere, no transfer/rotation
confusion. `mu = keccak256(keccak256(body))`; low-s with the identical constant; recovery id > 1
refused; zero/failed recovery refused; indices strictly increasing and `< n`; quorum `n*2/3 + 1`.
Expiry rejects `now > expires` (equality accepted) in all three; grace 86,400 s. Rotation: current
set only, `new_index == current + 1`, unique non-zero keys, advisory fields unchecked everywhere.
Governance emitter literal equals `keccak256("rand-bridge-governance")` and is byte-identical in
`Attestation.sol`, `bridge-codec` and both vector files; genesis refuses chain 1, the governance
emitter or zero in `emitters`. EVM 12-byte padding checked out of Rand (`check_burn`) and into the
endpoint. `fee <= amount`, zero amounts, `u64` cap on every lock and mint. Asset id =
`blake3("rand-bridge-asset" || chain BE || token)`. Rand mint: replay checked before recovery,
recipient-hash equality, gross mint. Burn: asset match, `burn == amount`, zero asset-bundle fee,
disjoint nullifiers/commitments, zk proof last. Effects before interactions on both endpoints.

Solana account model: owner + discriminator on every load, every account pinned by a re-derived
canonical-bump PDA, signer checks on every instruction, `Initialize` one-shot and gated on the
ProgramData upgrade authority, pre-funded PDAs handled (top-up / allocate / assign), token program
and mint owner pinned to classic SPL (Token-2022 refused), custody authority and mint checked,
`overflow-checks = true` in release. CLI: keys from env or file only; builders match the
processor's account order for all nine instructions.

The `tron/contracts` mirror is byte-identical to `evm/src`; `evmVersion: 'paris'` is pinned (no
`PUSH0`). Fullnode HEAD `a941774`: every "Verified fullnode facts" item in `AGENTS.md` still holds.
The 2026-09-17 findings (M-1 fixed; L-1–L-5, I-1–I-4) stand as written.

## 4. Token-specific pass: USDT and USDC on the four chains (same day)

The bridge was run against the **real** token contracts on forks of Ethereum and BNB Smart Chain
(`evm/test/ForkTokens.t.sol`; `FOUNDRY_PROFILE=fork ETH_FORK_URL=… BSC_FORK_URL=… forge test
--match-contract ForkTokensTest`): lock 100, release 40 with a relayer fee and the 10 bps protocol
fee, withdraw the fee, replay refused — for all four tokens, with exact balance assertions
(`custody + accruedFees == balanceOf(bridge)` throughout). All pass. **No new contract defect.**

| token | what is unusual | how the endpoint behaves |
|---|---|---|
| Ethereum USDT | `transfer` / `transferFrom` / `approve` return nothing; a dormant transfer fee (`basisPointsRate`, 0 today, max 20 bps); `pause`; blacklist on the *sender* | Empty returns accepted on the pull; the pay-out ignores return data and measures the balance. If Tether ever switches the fee on, locks revert (`TransferAmountMismatch`: custody could not be credited in full) and releases still work, the recipient bearing the fee. A pause makes releases revert with the digest unspent; they go through afterwards. Wallets must reset a non-zero allowance to 0 before changing it (USDT's `approve` rule) — a front-end matter. |
| Ethereum USDC | proxy, blacklist on sender **and** recipient, `pause` | A release to a blacklisted recipient reverts for good: that one burn is unreleasable (there is deliberately no re-route). A blacklisted *relayer* just means another relayer submits. |
| BSC USDT / USDC (Binance-Peg) | 18 decimals, upgradeable | Amounts are attested at 8 decimals; the sub-`1e10` remainder of a lock is never pulled. `DecimalsChanged` refuses a re-configuration if an upgrade ever moved `decimals()` under outstanding custody. |
| Tron USDT | `transfer` moves funds and returns `false`; `transferFrom` returns `true`; same dormant fee and blacklist as Ethereum's | H-1 above, fixed. To be confirmed on Nile with real test USDT before mainnet. |
| Tron USDC | **discontinued by Circle** (minting stopped February 2024, redemption ended February 2025) | Do not whitelist it (`docs/architecture.md` §10.1). Nothing in the contract needs to change: a token that is never `setToken`-enabled cannot be locked. |
| Solana USDT / USDC | classic SPL Token program (not Token-2022); freeze authority held by the issuer | The program pins the classic token program and refuses Token-2022 mints. A frozen recipient account fails that one release atomically (digest unspent). A recipient must be a *wallet*; the release pays its associated token account, which `rand-bridge-cli release` creates first. |

Issuer risk no contract can remove: Tether or Circle can freeze or blacklist the bridge's own
custody address, which would strand every note of that asset. It is the same risk every holder of
these tokens carries, scaled to the custody balance.

Operational finding: **a Tron release is expensive.** A release is up to two USDT transfers
(relayer fee, recipient) on top of five signature recoveries — roughly 300,000 to 450,000 energy,
30 to 45 TRX at the current 100 sun per unit (about $10 to $15), against well under $0.10 on
BSC or Solana. The relayer fee a Tron burn offers has to cover that, or the relayer has to stake
TRX for energy; at 10 bps the protocol fee only exceeds it above roughly $10,000 per release.
